# WasteFlow MVP Implementation Plan

## 1. MVP Objective

The first MVP must prove the complete operational loop:

```text
Create bins and roads
        -> simulate fill levels
        -> create collection requests
        -> prioritize urgent bins
        -> select an available truck
        -> calculate a route with Dijkstra
        -> display the route result
        -> mark bins collected
        -> update the database
```

The MVP is intentionally smaller than the final academic project. It establishes a reliable backend contract and a simple web interface. The current project also includes a COA teaching simulator; native assembly execution, authentication, reports, and 3D rendering remain outside the MVP.

## 2. MVP Technology Choice

### Backend

- Java 21 LTS
- Spring Boot 3.5.x or the current Spring Boot 3.x version available in Spring Initializr
- Maven
- Spring Web
- Spring Data JPA
- MySQL Driver
- Validation
- Flyway Migration
- Lombok, optional
- Spring Boot DevTools, development-only
- Spring Boot Actuator, optional but recommended

### Frontend

- React
- TypeScript
- Vite
- React Router
- TanStack Query
- Plain CSS or a small component library
- Canvas only for a basic route preview in the MVP

### Database

- MySQL 8.0+
- Docker Compose for local development

### Why this setup

Spring Boot gives the project a clear REST API, validation, transaction support, and database integration. JPA is suitable for the initial CRUD workflow; custom JDBC and custom academic data structures can be added later without changing the API contract. The algorithm code must remain independent of Spring so it can be tested and explained separately.

## 5. MVP Database Schema

The first migration should create only the tables required for the complete flow.

### `locations`

```text
id              BIGINT primary key auto_increment
name            VARCHAR(120) not null
x_coordinate    DOUBLE not null
y_coordinate    DOUBLE not null
created_at      TIMESTAMP not null
```

The x/y coordinates are sufficient for a campus or demo map. Latitude/longitude can be added later.

### `roads`

```text
id                    BIGINT primary key auto_increment
source_location_id    BIGINT not null
destination_location_id BIGINT not null
distance              DOUBLE not null
travel_time_minutes   DOUBLE not null
bidirectional         BOOLEAN not null default true
```

Add foreign keys to `locations`. Add checks ensuring distance and travel time are greater than zero.

### `waste_bins`

```text
id                BIGINT primary key auto_increment
bin_code          VARCHAR(40) unique not null
location_id       BIGINT not null
capacity_kg       DOUBLE not null
current_fill_kg   DOUBLE not null default 0
waste_type        VARCHAR(30) not null
status            VARCHAR(20) not null
last_collected_at TIMESTAMP null
created_at        TIMESTAMP not null
updated_at        TIMESTAMP not null
```

MVP statuses: `NORMAL`, `MEDIUM`, `HIGH`, `CRITICAL`, and `COLLECTED`.

### `trucks`

```text
id              BIGINT primary key auto_increment
truck_code      VARCHAR(40) unique not null
capacity_kg     DOUBLE not null
current_load_kg DOUBLE not null default 0
status          VARCHAR(20) not null
location_id     BIGINT not null
```

MVP statuses: `AVAILABLE`, `ASSIGNED`, `COLLECTING`, and `UNAVAILABLE`.

### `collection_requests`

```text
id              BIGINT primary key auto_increment
bin_id          BIGINT not null
priority_score  DOUBLE not null
urgency         VARCHAR(20) not null
status          VARCHAR(20) not null
created_at      TIMESTAMP not null
resolved_at     TIMESTAMP null
```

MVP request statuses: `PENDING`, `ASSIGNED`, `COMPLETED`, and `CANCELLED`.

Add a unique rule preventing multiple active requests for the same bin. This can be enforced in the service layer during the MVP.

### `routes`

```text
id                BIGINT primary key auto_increment
truck_id          BIGINT not null
algorithm         VARCHAR(40) not null
status            VARCHAR(20) not null
total_distance    DOUBLE not null
total_time        DOUBLE not null
created_at        TIMESTAMP not null
completed_at      TIMESTAMP null
```

### `route_stops`

```text
id                BIGINT primary key auto_increment
route_id          BIGINT not null
bin_id            BIGINT not null
sequence_number   INT not null
status            VARCHAR(20) not null
collected_kg      DOUBLE null
collected_at      TIMESTAMP null
```

## 7. MVP Business Rules

### Bin priority

Calculate:

```text
fillRatio = currentFillKg / capacityKg
```

Use these thresholds:

- Less than `0.50`: `NORMAL`
- `0.50` to less than `0.75`: `MEDIUM`
- `0.75` to less than `0.95`: `HIGH`
- `0.95` or more: `CRITICAL`

For the first version:

```text
priorityScore = fillRatio * 100
```

If two requests have the same score, process the older request first. Critical bins must appear before high, medium, and normal bins.

### Simulation

`POST /api/simulation/tick` should:

1. Select bins that are not currently being collected.
2. Increase `currentFillKg` by the configured amount.
3. Cap fill at `capacityKg`.
4. Recalculate the bin status.
5. Create a pending collection request when the bin reaches `HIGH` or `CRITICAL` and no active request exists.
6. Return changed bins and newly created requests.

The MVP uses a manual tick button. A background scheduler can be added later.

### Truck assignment

For the first version:

- Select the first `AVAILABLE` truck with enough capacity for the selected bins.
- Mark it `ASSIGNED` when a route is created.
- Allow only one active route per truck.
- If no truck can handle the route, return HTTP `409 Conflict` with a clear message.

### Collection

When a stop is completed:

1. Set collected quantity to the bin's current fill.
2. Set the bin fill to zero.
3. Set the bin status to `NORMAL`.
4. Mark its active collection request `COMPLETED`.
5. Reduce the truck current load by the collected quantity or reset it when the route ends.
6. Mark the route stop completed.

This operation must be transactional.


```json

  "truckId": 1,
  "requestIds": [1, 2, 3],

```

The route response must include:

```json
{
  "id": 1,
  "truckId": 1,
  "algorithm": "DIJKSTRA",
  "status": "ASSIGNED",
  "totalDistance": 42.5,
  "totalTime": 31.0,
  "stops": [
    {
      "sequenceNumber": 1,
      "binId": 3,
      "locationId": 5,
      "status": "PENDING"
    }
  ]
}
```

## 9. MVP Algorithm Implementation

Do not begin with every custom data structure. The minimum algorithm implementation is:

1. Build an in-memory adjacency-list graph from `Road` records.
2. Run Dijkstra from the depot location to each requested bin location.
3. Choose the next stop using highest priority, with shortest distance as the tie-breaker.
4. Repeat until all selected requests are assigned or truck capacity is reached.
5. Store the ordered route stops and calculated totals.

Create these plain Java classes under `route/algorithm` or a separate `algorithms` package:

```text
Graph
GraphNode
GraphEdge
DijkstraPathFinder
RoutePlan
RouteStopCandidate
```

The route algorithm must not access repositories directly. `RouteService` loads database records and passes simple data objects into the algorithm.

Later academic additions:

- Custom priority queue.
- Custom hash table for bin lookup.
- Greedy optimizer comparison.
- Operation counters and complexity dashboard.
- Brute-force route comparison for a small number of stops.

## 11. Implementation Order

### Step 1: Generate backend

Use the exact Spring Initializr configuration above. Confirm the generated project starts before adding features.

```powershell
cd backend
./mvnw spring-boot:run
```

On Windows PowerShell, use:

```powershell
cd backend
.\mvnw.cmd spring-boot:run
```

### Step 2: Start MySQL

From the repository root:

```powershell
docker compose up -d mysql
```

Confirm MySQL is reachable before starting the backend.

### Step 3: Add Flyway migration

Create `V1__create_mvp_schema.sql`, start the backend, and verify that all tables are created. Add `V2__insert_demo_data.sql` only after the schema succeeds.

### Step 4: Implement entities and repositories

Implement locations and roads first, followed by bins and trucks, then collection requests and routes. Use DTOs for controller input rather than accepting entities directly.

### Step 5: Implement bin CRUD

Add validation, service methods, controller endpoints, and tests. Verify that invalid capacity, negative fill, duplicate bin codes, and unknown locations return useful errors.

### Step 6: Implement simulation

Add manual simulation ticks, status classification, and request creation. Verify that repeated ticks do not create duplicate active requests.

### Step 7: Implement Dijkstra and route creation

Test Dijkstra with a small known graph before integrating it with the database. Then create the optimize endpoint and persist the route and stops in one transaction.

### Step 8: Implement collection completion

Add stop completion and route completion. Verify all related records update together and a failed operation does not partially update the database.

### Step 9: Add frontend

Create the three MVP screens: dashboard, bins, and route planner. Connect them to the backend through a single API client.

### Step 10: Add end-to-end verification

Run the full demo flow with seeded data and record screenshots for the project report.

## 12. MVP Testing Checklist

### Unit tests

- Fill ratio classification at `49%`, `50%`, `74%`, `75%`, `94%`, and `95%`.
- Priority ordering for critical, high, medium, and normal requests.
- Dijkstra shortest path with at least three nodes.
- Unreachable location handling.
- Truck capacity rejection.
- Duplicate active request prevention.

### API tests

- Create and retrieve a bin.
- Reject invalid bin input.
- Simulate a fill tick.
- Retrieve pending requests in priority order.
- Generate a route.
- Complete a route stop.
- Confirm bin fill resets to zero.

### Manual MVP demo

```text
1. Start MySQL.
2. Start Spring Boot.
3. Start the frontend.
4. Open the dashboard.
5. Click Simulation Tick.
6. Observe a high/critical request.
7. Select an available truck.
8. Generate a Dijkstra route.
9. Complete each stop.
10. Confirm the bin, request, truck, and route states changed.
```

## 13. MVP Completion Criteria

The MVP is complete when:

- The Spring Boot application starts with the configured MySQL database.
- Flyway creates the schema successfully.
- Demo data loads deterministically.
- Bin, location, road, and truck records can be viewed and edited.
- A simulation tick updates bin fill and creates collection requests.
- Requests are returned in priority order.
- Dijkstra generates a route over the stored road graph.
- Route and stop records are persisted.
- Collection completion updates the bin and request transactionally.
- The frontend can execute the full workflow without manually editing the database.
- Automated tests cover the fill logic, priority logic, shortest path, and main API path.

## 14. Excluded from MVP

Do not block the MVP on these features:

- Login and role-based security.
- WebSockets or real-time push updates.
- Real GPS or mapping APIs.
- 3D graphics, lighting, and texture mapping.
- Advanced Canvas algorithms such as DDA and Bresenham.
- Multi-truck optimization.
- IoT sensors.
- Machine learning prediction.
- Full custom implementations of every data structure.
- Native 64-bit assembly execution for COA calculations (the project currently provides a Java-based instruction simulator).
- Production deployment and cloud infrastructure.

These should be implemented as later milestones after the core route workflow is stable.
